# Logger

## Overview

PhotonIDE's logging system provides a lightweight, dependency-free way to record application events and diagnostic information.

The `Logger` class supports colored console output, timestamped messages, and optional file logging. It also distinguishes application messages from internal logging diagnostics.

**Source:** `core/logging/logger.py`

## Features

- Five severity levels: `DEBUG`, `INFO`, `WARNING`, `ERROR`, and `CRITICAL`.
- Color-coded console output using ANSI escape sequences.
- Timestamped log messages.
- Automatic creation of the `logs/` directory.
- File logging with UTF-8 encoding.
- Component-specific logger names.
- Shared logging configuration across instances.
- Console-only fallback when file operations fail.
- Validation of supported severity levels.

## Architecture

The logging system consists of the `Logger` class and a set of module-level configuration variables.

### Configuration

| Variable | Description |
|---|---|
| `COLORS` | Maps each supported severity level to its ANSI console color. |
| `VALID_LEVELS` | Set of supported severity levels, derived from `COLORS`. |
| `RESET_COLOR` | ANSI escape sequence that resets console formatting. |
| `log_file_path` | Path to the active log file. |
| `logger_initialized` | Indicates whether initialization has already been attempted. |
| `log_to_file_enabled` | Controls whether messages are written to the log file. |

The configuration variables are shared by all `Logger` instances within the same loaded module.

The first instance initializes the logging system. Subsequent instances retain their own component names but reuse the existing configuration and log file.

## Severity Levels

The logger supports five severity levels.

| Level | Console color | Intended use |
|---|---|---|
| `DEBUG` | Gray | Detailed diagnostic information. |
| `INFO` | Blue | Normal application events and status updates. |
| `WARNING` | Yellow | Unexpected conditions that may require attention. |
| `ERROR` | Red | Errors encountered during execution. |
| `CRITICAL` | Bright red | Severe errors requiring immediate attention. |

All supported levels are recorded. The current implementation does not filter messages according to severity.

Level names are case-insensitive when passed to `log()`.

## Usage

### Creating a logger

Create a `Logger` instance for the component that needs to record messages.

```python
from core.logging.logger import Logger

logger = Logger("PhotonIDE")
logger.info("Application started")
```

The logger name identifies the component that generated each message.

If `Logger` is exported from `core/__init__.py`, the shorter import can also be used:

```python
from core import Logger
```

### Logging messages

The class provides a dedicated method for each severity level.

```python
logger.debug("Loading application configuration")
logger.info("Application started")
logger.warning("Configuration file is missing")
logger.error("Failed to load a resource")
logger.critical("Application initialization failed")
```

Use `log()` when the severity level needs to be specified dynamically.

```python
logger.log("Background task completed", "info")
logger.log("Cache refreshed", "debug")
```

The default severity level for `log()` is `info`.

Unsupported levels raise a `ValueError`.

```python
logger.log("Example message", "invalid")
```

### Component-specific loggers

Multiple components can create their own logger instances.

```python
from core.logging.logger import Logger

editor_logger = Logger("Editor")
project_logger = Logger("Project")

editor_logger.info("Editor initialized")
project_logger.info("Project loaded")
```

Both instances share the same active log file, but their messages use different component names.

## Message Format

Each message follows this structure:

```text
[LEVEL] [YYYY-MM-DD HH:MM:SS] [COMPONENT] Message
```

Example:

```text
[INFO] [2026-10-14 14:30:00] [PhotonIDE] Application started
[WARNING] [2026-10-14 14:30:01] [Editor] Unsaved changes detected
[ERROR] [2026-10-14 14:30:02] [Logging] Failed to write to log file
```

Timestamps use the system's local date and time.

Console messages include ANSI color codes. The formatted messages written to log files do not include those color codes.

## Internal Logging

Messages generated by the logging system itself use `Logging` as their component name.

For example:

```text
[INFO] [2026-10-14 14:30:00] [Logging] Logger initialized
```

Internal errors are printed directly to the console through `_print_internal_error()`.

This method avoids depending on file logging to report failures involving the log directory or file.

Methods prefixed with an underscore are intended for internal use rather than direct calls by application components.

## Log File Management

### Directory

Log files are stored in the `logs/` directory, which is created automatically during initialization.

The directory path is relative to the application's current working directory, not the location of `logger.py`.

For example, if PhotonIDE starts from `D:\Projects\PhotonIDE`, the log directory is:

```text
D:\Projects\PhotonIDE\logs\
```

### Filename

Each log file uses the following naming convention:

```text
YYYY-MM-DD_HH-MM-SS.log
```

Example:

```text
2026-10-14_14-30-00.log
```

The timestamp has one-second precision. Consequently, filenames may collide if multiple logging initializations occur within the same second.

### File creation and writing

During initialization, the logger creates a new file and writes a header containing the creation timestamp.

Subsequent messages are appended to the active file using UTF-8 encoding.

## Error Handling

File operations are handled through `OSError` exception handling.

### Directory creation failure

If the `logs/` directory cannot be created, file logging is disabled. The system reports the failure directly to the console and continues in console-only mode.

### Initial file creation failure

If the log file cannot be created, file logging is disabled and the initialization message is still emitted to the console.

### Write failure

If writing a message fails, the system disables file logging and reports the error directly to the console.

Once file logging has been disabled, it is not automatically retried during the current process.

These behaviors allow console diagnostics to continue even when file operations fail.

## Implementation Limitations

The current implementation intentionally favors simplicity over advanced logging features.

- **Shared state:** All logger instances use module-level configuration and a shared log file.
- **Single initialization attempt:** Initialization is not automatically retried after failure.
- **Filename collisions:** Log filenames have second-level timestamp precision.
- **No rotation:** Log files are not automatically rotated, archived, or deleted.
- **No explicit synchronization:** Concurrent writes from multiple threads or processes are not explicitly coordinated.
- **Working-directory dependency:** The log directory depends on the process's current working directory.
- **ANSI support:** Console colors depend on the terminal or output environment supporting ANSI escape sequences.

These limitations should be considered if PhotonIDE later requires more advanced logging capabilities.

## Design Principles

The logging system follows these principles:

- Keep the implementation lightweight and dependency-free.
- Provide consistent formatting across application components.
- Separate application messages from internal logging diagnostics.
- Preserve console output when file logging is unavailable.
- Document non-obvious behavior without duplicating implementation details.
