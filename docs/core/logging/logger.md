# Logger Module

## Overview

The `logger.py` module provides the public interface for the PhotonIDE logging system. It defines the `Logger` class, which allows application components to record messages at different severity levels.

The module coordinates logging initialization and delegates message formatting and output operations to the appropriate internal modules.

## Responsibilities

The `Logger` class is responsible for:

- Associating log messages with a specific application component.
- Initializing the shared logging system when the first logger instance is created.
- Providing convenience methods for supported log severity levels.
- Exposing timestamp and log filename utilities.
- Delegating message processing and output to the logging handlers.
- Recording internal messages generated by the logging system.

## API Reference

### `Logger(name: str)`

Creates a logger associated with a specific application component.

**Parameters**

| Parameter | Type | Description |
|---|---|---|
| `name` | `str` | Name of the component that generates log messages. |

**Behavior**

When the first `Logger` instance is created, the logging system is initialized through `handlers.initialize_logging()`.

Subsequent instances reuse the shared logging configuration and output destinations instead of initializing the system again.

**Example**

```python
from core.logging import Logger

logger = Logger("Application")
logger.info("Application started.")
```

### `log(message: str, level: str = "info")`

Records a message using the component name associated with the logger.

**Parameters**

| Parameter | Type | Description |
|---|---|---|
| `message` | `str` | Message content to record. |
| `level` | `str` | Severity level. Defaults to `info`. |

**Example**

```python
logger.log("Loading project configuration.", "debug")
```

An unsupported severity level raises a `ValueError` in the underlying logging handler.

### Severity-Specific Methods

The class provides convenience methods for the five supported severity levels.

| Method | Severity | Intended Use |
|---|---|---|
| `debug(message)` | `DEBUG` | Diagnostic information useful during development. |
| `info(message)` | `INFO` | General application events and status updates. |
| `warning(message)` | `WARNING` | Conditions that may require attention. |
| `error(message)` | `ERROR` | Errors encountered during application execution. |
| `critical(message)` | `CRITICAL` | Serious errors requiring immediate attention. |

Each method accepts a message string and delegates to `log()` with its corresponding severity level.

**Example**

```python
logger.debug("Checking project dependencies.")
logger.info("Project loaded successfully.")
logger.warning("Configuration file is missing.")
logger.error("Unable to open project file.")
logger.critical("A critical application error occurred.")
```

### `get_timestamp() -> str`

Returns the current local date and time.

The method delegates to `formatters.get_timestamp()`.

**Return format**

```text
YYYY-MM-DD HH:MM:SS
```

**Example**

```python
timestamp = logger.get_timestamp()
```

### `get_file_name() -> str`

Generates a log filename based on the current local time.

The method delegates to `formatters.get_file_name()`.

**Return format**

```text
YYYY-MM-DD_HH-MM-SS.log
```

**Example**

```python
filename = logger.get_file_name()
```

### Internal Methods

The following methods support the internal logging architecture. They are intended for use by the logging system rather than as the primary application-facing API.

#### `_log_message(name, message, level="info")`

Delegates message processing and output to `handlers.log_message()`.

It accepts an explicit component name, message content, and severity level.

#### `_log_internal(message, level="info")`

Records a message generated by the logging system itself. Internal messages use `Logging` as their component name.

#### `_print_internal_error(message)`

Delegates internal error reporting to `handlers.print_internal_error()`. This method allows logging failures to be reported directly to the console without relying on normal file logging.

## Logging Architecture

The `Logger` class acts as the interface between application code and the internal logging modules.

The responsibilities are divided as follows:

- **`config.py`** — Stores severity configuration, ANSI color codes, and shared logging state.
- **`formatters.py`** — Generates timestamps and filenames and formats log messages.
- **`handlers.py`** — Initializes logging destinations and writes messages to the console and log file.
- **`logger.py`** — Exposes the `Logger` class and its severity-specific methods.

This separation keeps the public interface simple while isolating formatting, configuration, and output handling.

## Initialization Behavior

The logging system uses the shared `config.logger_initialized` flag to determine whether initialization has already occurred.

When a `Logger` instance is created:

1. The instance stores its component name.
2. It checks whether the logging system has already been initialized.
3. If initialization has already occurred, the constructor returns.
4. Otherwise, it marks the system as initialized and delegates initialization to `handlers.initialize_logging()`.

This approach prevents every logger instance from creating a separate log file.

The initialization flag is set before the initialization handler runs. If initialization fails, the handler is responsible for reporting the error and disabling file logging when necessary.

## Usage Example

A typical application component can create a logger and use it throughout its implementation.

```python
from core.logging import Logger

logger = Logger("ProjectManager")

def load_project(path: str) -> None:
    logger.info(f"Loading project: {path}")

    try:
        # Project loading logic goes here.
        logger.info("Project loaded successfully.")
    except Exception as error:
        logger.error(f"Failed to load project: {error}")
        raise
```

Each message is associated with the `ProjectManager` component name and is passed to the shared logging system.

## Dependencies

The module depends on the following internal modules:

- `config.py` — Shared initialization state.
- `formatters.py` — Timestamp and filename utilities.
- `handlers.py` — Initialization, error reporting, and message output.

No external dependencies are required by this module.

## Design Considerations

### Shared Logging State

All logger instances use the same logging configuration and output destinations. Creating a logger for another component does not independently initialize the logging system.

### Separation of Concerns

The class delegates formatting and output operations instead of implementing them directly. This makes the public interface easier to maintain and allows internal behavior to evolve independently.

### Component Identification

Each logger instance stores a component name. Messages recorded through its public methods use that name to identify the source of the event.

### Internal Error Handling

Internal logging errors are reported through dedicated handler methods. This prevents failures in normal file output from requiring the same output mechanism that has already failed.

### Convenience Methods

Severity-specific methods provide a clear and consistent API, avoiding the need for application code to pass a severity string to every logging call.

## Limitations

- The logger uses shared module-level state rather than independent configurations for each instance.
- Initialization is controlled by a boolean flag and does not provide explicit reinitialization or shutdown methods.
- Timestamp and filename generation use the local system clock.
- The logger does not implement filtering thresholds, asynchronous output, log rotation, or structured logging.
- The class does not provide built-in exception traceback formatting; callers must include any required diagnostic information in their messages or handle it separately.
- The underscore-prefixed methods are implementation details and should not be treated as the primary public API.
